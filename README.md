# SPYDER — spyder.ac website (v3)

Premium, bilingual (EN/RU) informational site for the SPYDER ecosystem. Static HTML/CSS/JavaScript — no Node build stage, third-party analytics, cookies for tracking or web wallet key handling. Official logo assets were extracted from the SPYDER native iOS source previously supplied for this project.

## Website pages

| Route | Purpose |
| --- | --- |
| `/` | Landing page, wallet preview, ecosystem, feature stories, roadmap, FAQ |
| `/wallet.html` | Spyder Wallet overview and native app concept |
| `/network.html` | Spyder Network / messaging concept |
| `/chain.html` | Chain and planned SPD information |
| `/security.html` | Safety and anti-phishing guidance |
| `/download.html` | **NEW** Official distribution availability; verified destinations only |
| `/support.html` | **NEW** Searchable self-service FAQ in EN/RU, processed locally |
| `/privacy.html`, `/terms.html` | Website-specific preliminary legal notices (require operator review) |
| `/404.html` | Branded missing-page experience |

Public distribution links, blockchain mainnet metrics, public audits and token listings are **not claimed** until verified. Web previews are not live wallet screens. The web site cannot receive money, access a seed phrase, sign transactions or authenticate users.

## Local preview

```bash
python3 -m http.server 8000 --directory site
python3 scripts/validate_site.py
node --check site/assets/app.js
```

Open `http://localhost:8000`. Optional browser regression checks can be run locally using Playwright with Chromium; no browser testing tool is required to deploy the static site.

`site/assets/` contains site-only static assets; there is no bundler or cloud build step. Edit `site/index.html` directly; **four product pages** are generated by `scripts/build_pages.py`. New `download.html` and `support.html` are maintained directly. Do not run the product-page generator without inspecting its diff before release.

## GitHub ZIP update

Use an archive called `spyder-web-update*.zip` in the repository root, containing root-relative paths like `site/index.html`, with no outer folder and **no `.github/workflows/`**. The `SPYDER Web — Unpack` action overlays it and runs `scripts/validate_site.py` and `node --check` **before** committing the changes. If validation fails, the job is red and the ZIP remains in the repository so deployment does not proceed. Only after a successful unpack may the Worker deployment workflow run.

**Required separate workflow update with v3:** `.github/workflows/spyder-web-unpack.yml` must be replaced manually with `spyder-web-unpack-v3.yml`. The existing `.github/workflows/spyder-cloudflare-pages.yml` is unchanged and must remain present. Despite the latter filename, it currently deploys a Cloudflare **Worker** (not Pages). The Worker name in the current repository is intentionally **`spider-ac`**; `spyder.ac` is the domain name. Do not rename the Worker or link to another Cloudflare project without a controlled migration.

## Cloudflare Workers static assets

The existing workflow deploys the `site/` directory using Wrangler 4 to the existing Worker `spider-ac`; it requires these GitHub Actions secrets:

- `CLOUDFLARE_API_TOKEN` with appropriate Workers deployment permissions
- `CLOUDFLARE_ACCOUNT_ID` for the correct Cloudflare account

The domain must remain correctly associated with this Worker under Cloudflare's Domains & Routes. The `_headers` file sets content and security headers for static assets. Its asset cache max-age is five minutes because CSS/JS asset filenames are currently non-fingerprinted.

**Release precautions:** The ZIP extraction workflow cannot commit to a protected `main` without the necessary bot permissions or a configured exception. Browser checks, GitHub Actions, Cloudflare authorization and production domain routing are separate validation steps. An archive passing local tests does not prove a successful Cloudflare production deployment.
